# 对账单字段映射 — 微信 / 支付宝（批C 对账分流，微信支付预留 2026-09-08）

> 方案依据：`方案v2-微信支付预留-20260908.md` §3.3（D6/D7）；验收清单 §3 T3。
> 性质：**预留文档** —— 本轮只建表结构（`ReconciliationLedger` / `StatementImportBatch`）+ 本映射说明，**不做真实导入解析代码**（D7）。真实接入（微信商户号/支付宝资质就绪后）按本文口径实现导入器。

## 一、台账表速览（`reconciliation_ledger`）

| 列 | 类型 | 写入方 | 说明 |
|---|---|---|---|
| `order_id` | uuid, **@unique** | 写入钩子 | **幂等锚点**：同单多事件只写一行（与 `CashCollection.orderId` 同构） |
| `order_no` | text | 写入钩子 | 订单号快照，**对账单匹配主键**（免 join orders） |
| `payment_method` | enum(PaymentMethod) | 写入钩子 | 资金渠道：`COD` / `BANK_TRANSFER` / 线上渠道（导入时） |
| `amount_usd` | int 分 | 写入钩子 | 实收金额（USD 分）：COD=骑手实收（拒付=0）；线上=PaymentIntent.amount |
| `exchange_rate` | int 万分位，可空 | 写入钩子 / 导入 | 汇率快照（同 `Order.exchangeRate` 口径）；纯 USD 资金流 null |
| `amount_cny` | int 分，可空 | 写入钩子 / 导入 | 人民币金额（分）；纯 USD 资金流 null |
| `cash_result` | text，可空 | COD 钩子 | `PAID` / `SHORT` / `UNPAID`（口径同 `CashCollection.result`）；线上渠道 null |
| `status` | enum | 钩子→导入→结算 | 状态机 `PENDING → MATCHED / DIFF → SETTLED` |
| `statement_batch_id` | uuid，可空 | 导入 | 回填批次（`statement_import_batches.id`） |

**现有写入钩子**（本轮已实现）：

- **COD**：`dispatch.service.ts deliverTask` 事务内（`tx.cashCollection.create` 同事务，R8 落点）——覆盖 PAID/SHORT/**UNPAID**（拒付未实收 amountUsd=0 也写，见 T3-1）
- **BANK_TRANSFER**：`admin-payment.controller.ts confirm-receipt` 事务内（审核通过）
- **线上渠道（WECHAT/WECHAT_GLOBAL/ALIPAY_CN）**：未来对账单导入 MATCHED 时写（本轮不产生数据）

**金额单位约定**：全表金额为 **int 分**（cents）。微信/支付宝账单金额为**元（两位小数）**，导入时 `× 100` 取整。

## 二、微信支付（国内商户号）对账单 → 台账映射

**来源**：微信商户平台 → 交易中心 → 交易账单（按日下载 CSV，zip 内 CSV 为 **GBK 编码**，导入器必须转码）。
下表字段名以《交易账单数据结构（新版）》为准；**实际接入时以所下载账单表头为准做适配层**，表头变更只改适配层不动台账。

| 台账列 | 微信账单字段 | 换算 / 说明 |
|---|---|---|
| `order_no` | 商户订单号（`out_trade_no`） | **匹配键**：MeiMart 下单时以 orderNo 作商户侧单号 |
| `payment_method` | （常量） | 该账单整体为 `WECHAT`（国际版另出 `WECHAT_GLOBAL` 账单，不适用东帝汶，仅占位） |
| `amount_usd` | —（回查订单） | 账单为 CNY 金额；USD 金额回查 `PaymentIntent.amount`（或订单 payableAmount） |
| `amount_cny` | 订单金额（`订单金额` 列，非入账金额） | `× 100` 转 int 分；**用订单金额口径，不含手续费**（手续费进结算域不进台账） |
| `exchange_rate` | 反推 | `round(amount_cny / amount_usd × 10000)` —— **实际成交汇率**（万分位），与下单快照可能不同（见 T3-3） |
| `cash_result` | （恒 null） | 非 COD 渠道 |
| `status` | 匹配结果 | 账单行匹配到台账/订单 → `MATCHED`；金额对不上 → `DIFF`（阈值见 T3-3） |
| `statement_batch_id` | （导入时回填） | 指向本次导入批次行 |

**交易状态（交易状态列）→ 处理口径**：

| 账单交易状态 | 口径 |
|---|---|
| `SUCCESS`（支付成功） | 正常匹配，写线上台账行 |
| `REFUND`（退款） | **不新建台账行**，走 T3-2 退款口径 |
| `REVOKED` / `PAYERROR` / `CLOSED`（撤销/失败/关闭） | 不写台账行；该订单若已有台账行则不匹配 → 计入异常清单 |

## 三、支付宝（中国）商家账单 → 台账映射

**来源**：支付宝商家平台 → 对账中心 → 商家账单（交易账单明细，CSV，**GBK 编码 + 首行表头说明行**——导入器需跳过前几行说明/表头，以"###"分隔行为准）。

| 台账列 | 支付宝账单字段 | 换算 / 说明 |
|---|---|---|
| `order_no` | 商户订单号 | **匹配键**（同微信） |
| `payment_method` | （常量） | 该账单整体为 `ALIPAY_CN` |
| `amount_usd` | —（回查订单） | 同微信（账单为 CNY） |
| `amount_cny` | 金额（元）列中**业务收/支 = 收入且交易状态成功**的行 | `× 100` 转 int 分；剔除余额/利息/转账类非交易行 |
| `exchange_rate` | 反推 | 同微信（实际成交汇率） |
| `cash_result` | （恒 null） | 非 COD 渠道 |
| `status` | 匹配结果 | 同微信（`MATCHED` / `DIFF`） |
| `statement_batch_id` | （导入时回填） | 同微信 |

**交易状态（交易状态列）→ 处理口径**：`交易成功` → 匹配写行；`退款成功` → 走 T3-2；`等待买家付款` / `交易关闭` → 不写行、计异常清单。

## 四、BANK_TRANSFER 银行流水单（补充口径）

银行对账单无统一格式（东帝汶本地银行各异），本轮不定义列映射；仅约定：

- `format = BANK`；匹配键同为 `order_no`（人工对账时按转账备注/凭证单号回查）
- 银行流水为 **USD**：`amount_usd = 流水金额 × 100`，`exchange_rate` / `amount_cny` 保持 null
- 现状人工对账流程（凭证上传 → admin `confirm-receipt` 审核 → 台账 PENDING）不变，流水导入为后期增强

## 五、T3 异常口径（验收清单 §3 T3）

### T3-1 未支付

- **判定**：系统侧台账 `PENDING` 且订单仍未支付（PaymentIntent 非 PAID），**或** 用户选了线上渠道但从未发起/完成支付（无台账行）——两者都**不会**在账单中出现匹配行。
- **处理**：导入器按「账单有、系统无」与「系统有（PENDING）、账单无」双向核对，输出**异常清单**（不入台账）；台账行保持 `PENDING`，超期（>7 天）由运营人工关闭订单。
- COD 拒付（`UNPAID`）**不属于**线上未支付：它已入台账（`amountUsd=0, cashResult=UNPAID`），属资金流已闭环的异常实收。

### T3-2 退款

- 台账行**只记正向资金流入账**，退款金额**不回改** `amount_usd / amount_cny`（退款走 Refund 域 P13 体系独立对账）。
- 账单出现退款行（微信 `REFUND` / 支付宝 `退款成功`）：匹配该订单台账行，若为**全额退款** → 行状态置 `DIFF`（备注差异类型 `FULL_REFUND`）；部分退款保持 `MATCHED`，退款差额由 Refund 域核对。
- 台账 `status` 不直接推进到 `SETTLED`：结算闭环（Settlement 域）确认后才置 `SETTLED`。

### T3-3 汇率差异

- 三个汇率来源：**下单快照**（`Order.exchangeRate`，批A 锁定，显示/预估口径）、**实际成交汇率**（账单反推 `amount_cny / amount_usd`）、**兜底汇率**（当日无表时下单用的 FALLBACK 值）。
- 对账判定：`|账单实付 CNY − 订单快照 estimatedCnyAmount|` 超过阈值（建议快照金额的 **1%**，实施时配置化）→ 台账行置 `DIFF`，差异类型 `RATE_DELTA`；阈值内仍 `MATCHED`（微小波动正常）。
- 差异根因：快照锁定到支付完成存在时间差 + 通道方汇率/手续费。**显示与结算一律用快照值**（方案 D5），账单差异只进对账报告，不改订单/结算金额。

## 六、与 Settlement 结算单的分工（防重复建设，方案风险 10）

| | ReconciliationLedger（台账） | Settlement（结算单） |
|---|---|---|
| 对象 | **资金流**（每一笔收入的渠道/币种/到账核对） | **主体结算**（商家/骑手按周期应收应付聚合） |
| 粒度 | 订单级、含渠道与汇率维度 | 周期 × 主体聚合（`periodDate, subjectType, subjectId`） |
| 状态机 | PENDING → MATCHED/DIFF → SETTLED | 结算域自有状态 |
| 修改 | 本轮不动 Settlement 结构 | 对账 SETTLED 仅是台账自身状态推进，不回写 Settlement |

台账 `SETTLED` ≠ Settlement 生成；两者由未来的结算闭环流程衔接，本轮互不影响。
